# 以太坊钱包系统 (eth-scan) 业务介绍

## 一、系统概述

本系统是一个托管式以太坊钱包平台，为每个用户分配独立的以太坊充值地址，通过扫块引擎实时监控链上入账，并支持代币归集、提现转账与 Lido 质押等业务。

---

## 二、核心数据模型

### 1. 用户表 (users)

平台用户的基础信息表，是整个业务的主体。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uint64 | 主键 |
| username | varchar | 用户名 |
| created_at | timestamp | 注册时间 |

### 2. 主地址表 (master_wallets)

通过一个助记词（Mnemonic）派生出所有子地址的根。系统中可存在多个主地址，用于隔离不同业务线或扩容。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uint64 | 主键 |
| mnemonic_encrypted | varchar | 加密后的助记词（明文禁止落库） |
| address | varchar(42) | 主地址的公开以太坊地址 |
| derive_count | uint32 | 已派生的子地址数量（用于续派） |
| created_at | timestamp | 创建时间 |

> 派生规则：BIP-44 路径 `m/44'/60'/0'/0/{index}`，index 从 0 开始自增。

### 3. 以太坊地址表 (eth_addresses)

从主地址派生出的子地址，每个地址与一个用户绑定，用于接收充值。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uint64 | 主键 |
| master_wallet_id | uint64 | 关联主地址 |
| user_id | uint64 | 关联用户（0 表示未分配） |
| address | varchar(42) | 以太坊地址（小写存储） |
| derive_index | uint32 | BIP-44 派生索引 |
| status | tinyint | 状态：0=未使用 1=使用中 2=已禁用 |
| assigned_at | timestamp | 分配给用户的时间 |

> - 地址预生成后放入空闲池，用户注册或首次充值时从池中分配一个未使用地址并与 user_id 绑定。
> - 禁用状态的地址不再参与扫块监控，也不会被重新分配。

### 4. 交易流水表 (transactions)

记录每笔命中监控地址的链上交易，是充值到账的凭证。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uint64 | 主键 |
| user_id | uint64 | 关联用户 |
| tx_hash | varchar(66) | 交易哈希（唯一索引，防重入） |
| from_address | varchar(42) | 发送方地址 |
| to_address | varchar(42) | 接收方地址（我方监控地址） |
| value | varchar(80) | 金额（Wei，字符串存储防精度丢失） |
| token_type | varchar | 币种：ETH / USDT / ... |
| block_number | uint64 | 所在区块高度 |
| block_time | timestamp | 区块时间 |
| status | tinyint | 0=待确认 1=已确认 2=已到账 |
| created_at | timestamp | 入库时间 |

### 5. 扫块进度表 (scan_heights)

记录扫块引擎当前已扫描到的高度，服务重启后从此处续扫，防止漏单。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | uint64 | 主键（通常只有 1 条记录） |
| chain | varchar | 链标识（如 `ethereum`、`sepolia`） |
| block_number | uint64 | 最后成功处理的区块高度 |
| updated_at | timestamp | 更新时间 |

## 三、核心业务流程

### 流程 1：地址分配（用户开通充值）

```
用户请求充值地址
  → 查询 eth_addresses 中 status=0（未使用）的地址
  → 若地址池不足，触发批量派生（从主地址按 derive_count 续派 N 个）
  → 将地址 status 置为 1（使用中），写入 user_id
  → 将该地址加入扫块引擎的 watchAddressMap
  → 返回地址给用户
```

### 流程 2：充值到账（扫块引擎）

```
EthScanner.Start(ctx)
  → 从 scan_heights 读取上次扫描高度
  → 循环：GetLatestBlockNumber → 落后 12 块确认 → GetBlockByNumber
  → processBlock：遍历每笔交易，比对 tx.To 是否在 watchAddressMap
  → 命中 → GetTransactionReceipt 确认 status==1（交易成功）
  → 写入 transactions 表（tx_hash 唯一索引防重复）
  → 更新 scan_heights
  → 通知业务层（更新用户余额 / 发 MQ 消息）
```

> ETH 充值：直接读取 `tx.Value`。
> ERC20（USDT）充值：需解析 `eth_getLogs` 中的 Transfer 事件，Topic[0] = `keccak256("Transfer(address,address,uint256)")`。

### 流程 3：提现转账

```
用户发起提现
  → 校验用户余额充足
  → 从主地址（归集钱包）发起转账
  → GetTransactionCount 获取 Nonce（优先从本地 Nonce 计数器取）
  → GetSuggestGasPrice / EstimateGas 估算手续费
  → 本地私钥离线签名（types.SignTx）
  → SendRawTransaction 广播
  → 记录提现流水，等待确认回调
```

### 流程 4：ETH 归集

```
扫块发现 ETH 充值到账
  → 判断余额 > eth_min_gas_amount（最小归集阈值，来自 config.yaml）
  → 从子地址向归集主地址发起 ETH 转账
  → 归集成功后子地址余额清零，等待下次充值
```

### 流程 5：Lido 质押

```
调用 lido_handler.go
  → 构造 calldata：0xa1903eab + referral_address（32 字节）
  → 将 ETH 数量作为 msg.value（Wei）
  → 通过 SendRawTransaction 广播到 Lido 合约
  → 用户获得等值 stETH
```

## 四、地址派生规则

使用 BIP-44 标准，所有子地址从同一助记词确定性派生，只需备份助记词即可还原所有子地址私钥：

```
路径：m / 44' / 60' / 0' / 0 / {index}
         │      │      │    │    │
         │      │      │    │  子地址序号（derive_index）
         │      │      │  外部账户（固定 0）
         │      │   账户（固定 0）
         │   ETH 主链
       BIP-44
```

- `derive_index` 存储在 `eth_addresses.derive_index`，每次派生新地址后 `master_wallets.derive_count++`。
- 私钥在内存中即用即销，只将加密后的助记词存库。

## 五、watchAddressMap 刷新机制

扫块引擎内存中维护 `map[string]uint64`（地址 → 用户ID），避免每笔交易都查数据库：

- **启动时**：`FreshWatchAddressMap()` 全量加载 `eth_addresses` 中 `status=1` 的地址。
- **运行中**：新地址分配后，通过接口或 MQ 通知 scanner 调用 `AddWatchAddress()` 增量写入（加写锁）。
- **禁用地址**：将地址从 map 中删除，扫块不再监控。

## 六、安全与风险控制

| 规则 | 原因 |

|------|------|
| 助记词/私钥只以加密形式落库 | 泄漏即资产损失，不可逆 |
| 交易入库以 tx_hash 为唯一索引 | 防止扫块重启导致的重复到账 |
| 充值需 12 块确认才计入余额 | 防止链分叉导致的双花 |
| 所有 RPC 调用带 10s 超时 context | 防止节点超时阻塞扫块主循环 |
| 金额全程使用 `math/big.Int`（Wei） | 防止 float64 精度损失 |
| Nonce 本地计数器 + 失败回滚 | 防止高并发提现时 Nonce 冲突 |
